Chapter 6 · what we built Our build · not Groupon's data, not Groupon's system

Could a system have known?

The supplied log cannot answer this. It records how many results came back and never which ones, so there is nothing in it to test detection against — the same gap Chapter 5 had to go to production to work around. So we built the detector instead and measured it.

The test is only worth something because the two halves are independent: the labels come from the analysis, the scores come from the build, and neither saw the other. What follows is the one place on this page where the measurement is of our own work rather than of Groupon's.

Try the working version

Chapter 4 replays the logged set from this file with the network off. That constraint is deliberate — this page has to open from a laptop with the wifi down — and it is why the replay is a lookup rather than a search.

The prototype is the other one. Same argument, real retrieval, its own page: it handles every query class this analysis found, including the ones nothing can fix, which is the part Groupon’s current UI has no design for.

What it does that today’s search does not
Names what is missing “We don’t have skydiving in Berlin” — the query and the city, not “no results found” and never “remove a filter” when no filter was applied.
Labels alternatives as alternatives A substitute is shown inside a container that says it is one. That single sentence is the whole difference from the Similar deals carousel.
Treats 1–2 results as near-empty The abstention panel first, at full width; the one or two real deals below it. Chapter 1’s cliff, rendered as a screen.
Turns the dead end into information Notify-me writes to a demand table, which is the only route by which Chapter 2’s largest bucket — the one search cannot fix — reaches the team that can.
Status, stated before anyone clicks The prototype is built and it runs — hosted, behind this button. It handles every query class this analysis found — including the ones search cannot fix — plus two the classification never named: a city that stocks none of what the market matched, and a query from outside the logged set, which it refuses by name rather than guessing. Every abstention and every city-empty dead end writes itself to the demand table; notify-me writes a second, separate row, because “we had nothing” and “tell me” are different facts. The hosted database has been migrated and seeded — schema, seeds and embeddings, all of them the analysis's own — so the search behind this button answers from the same data the chapters above were computed from. The rest of the package is here. A demo that overstates itself undoes the honesty the six chapters above it are built on, and it is the one claim on this page a reader can check in ten seconds.

The limits · the supplied data, live production and our build

The limits, stated

The brief grades whether claims survive being checked. These are the places where they would not, said before anyone has to find them.

"Same city" means stock existed nearby — not that it would have satisfied the searcher. A deal titled "Spa & Massage Treatment" counts as the answer to sports massage. This inflates the search bucket, and it is the load-bearing assumption of Chapter 2.
The two biggest errors here push in opposite directions and they are stated rather than netted against each other. The one above inflates the search problem; the can't-tell dead ends inflate the supply problem. Neither is quietly resolved in our own favour.
The size of silent substitution is inferred, not observed. The supplied log has no query→deal mapping, so "these users saw the wrong thing" is read off the catalogue. Chapter 5 shows the mechanism is real in production; it does not size it here.
One class's stated basis was falsified by our own Chapter 2. The geographic class was justified as "stocked in the market, not in this city" — but only of of its dead ends actually are. Its recoverability was left at the more generous value rather than re-cut, and the tightened figure is shown in Chapter 3.
Recovered demand is converted at the healthy rate — an upper bound. Demand that already failed once converts worse than demand that never did.
The classifier is accurate, self-audited by the author of its own rules, so that figure is an upper bound too.
The data is clean enough to be synthetic. The supply void is a property of this catalogue. Live production is thin on the same concepts rather than empty — — so the shape is not merely an artifact. But no number about real Groupon's inventory follows from it either.
No search in the supplied data returns exactly three results — the distribution runs 0, 1, 2, then 4. Live Groupon returns routinely (), so this is a property of how the data was generated.
The language fix is partial, and Chapter 3 is an upper bound because of it. Our own build bridges the phrasing gap on of Chapter 3's matched pairs and fails to bridge of them. Chapter 3's recoverability range was set before that was measured and has not been re-cut downward. Measured on our build · chapter 5
